## 1. 论文基本信息

**《Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory》**
- arXiv: 2504.19413（2025-04）
- 作者：Prateek Chhikara, Dev Khant, Saket Aryan 等（mem0 团队）
- 两个贡献：① Mem0 主架构（两阶段管线 + 向量库）；② Mem0g 图记忆扩展；③ LoCoMo 系统评测

## 2. Mem0 主架构（论文视角，与 03-原理篇对应）

- **提取阶段**：当前消息对 + 会话摘要 + 近期消息 → 产出候选记忆（显著事实）
- **异步摘要模块**：并行持续刷新会话摘要，保证提取时全局上下文最新
- **更新阶段**：候选事实 + top-s 相似记忆 → LLM 通过**工具调用**决定 ADD/UPDATE/DELETE/NOOP
- **类比锚点**：人类 = 便签本（近期对话）+ 归档柜（蒸馏后的事实），存的是"要点"不是"录音"

## 3. Mem0g 图记忆架构（论文版）

- **表示**：有向标记图 G=(V, E, L)：节点=实体，边=关系三元组（含类型标签，如 `用户A -[偏好]-> 早上会议`）
- **构建**：两阶段 LLM 管线——**实体抽取器**（识别人/地/物/概念/事件 + 重要性分析）→ **关系生成器**（产出关系三元组），再经冲突检测后更新 **Neo4j** 图
- **检索**（双路）：
  1. **实体中心法**：定位关键实体 → 沿边探索子图 → 拼装相关上下文
  2. **语义三元组法**：query 与图三元组做 embedding 匹配
- **强项**：结构化保留关系与时序 → **时序推理**最好的记忆方案之一

## 4. LOCOMO 实验（重点数据 + 正确解读）

**实验设置**：LoCoMo 数据集 = 10 段超长对话（平均 600 轮、~26k token）× 每段 ~200 问题；四类题型：单跳 / 多跳 / 时序 / 开放域；指标：J（LLM-as-a-Judge）、F1、BLEU-1 + 部署指标（延迟、token）。

### 4.1 总表

| 方案 | 综合 J | 特点 |
|---|---|---|
| **全量上下文**（上界） | **72.90%** | p95 延迟 17.12s、~26k token/轮，成本不可行 |
| **Mem0g**（图） | **68.44%** | 时序/开放域强 |
| **Mem0**（向量） | **66.88%** | 延迟/token 最低 |
| 最强 RAG 配置 | ~61% | — |
| A-Mem | ~52.9% | Mem0 比 A-Mem 高 13.98 |
| LangMem | 58.10% | — |
| OpenAI 记忆 | 52.90% | Mem0 单跳比它高 3.34 |

### 4.2 分项亮点

| 题型 | 冠军 | 数据 |
|---|---|---|
| 单跳 | Mem0 | J=67.13（+3.34 vs OpenAI） |
| 多跳 | Mem0 | J=51.15 |
| 时序 | **Mem0g** | F1=51.55 / J=58.13 |
| 开放域 | Zep | J=76.60（Mem0g 75.71 紧随） |

### 4.3 效率数据（工程最关心）

- 检索延迟：Mem0 p50 **0.148s** / p95 **0.200s**
- 总延迟：Mem0 中位 **0.708s**；p95 **1.44s**（比全量上下文**低 91%**）
- 记忆 token 开销/对话：Mem0 ≈ **7k**，Mem0g ≈ **14k**（图表示翻倍），Zep **>600k**（比原始对话还大 20 倍）
- 图构建时效：Mem0g 一分钟内完成 vs Zep 数小时延迟

### 4.4 正确解读（防误导）

1. ✅ "精度接近全量上下文、成本延迟低一个量级"——成立，这是核心结论
2. ⚠️ 精度**没有**超过全量上下文（66.9/68.4 vs 72.9），别被营销话术带偏
3. ⚠️ 基准是**对话记忆**场景，不等于你的业务场景；官方建议用自有数据评测（见 06-生产篇）
4. ⚠️ 论文自认局限：开放域略逊 Zep；仅文本；冲突检测全靠 LLM；未融合分层记忆

## 5. 现役 Graph Memory vs 论文 Mem0g（关键辨析！）

**这是两代东西**。读旧教程最容易在这里翻车：

| 维度 | 论文 Mem0g（2025-04） | 现役 Platform Graph Memory（2026） |
|---|---|---|
| 存储 | 外接 **Neo4j** 图数据库 | **平台内置**，无需部署任何图库 |
| 边类型 | **带类型三元组**（LLM 生成关系标签） | **无 schema、无类型标签**：共享实体的记忆互连（共现推断） |
| 构建方式 | 实体抽取器 + 关系生成器两阶段管线 | 实体提取 → 实体成为节点 → 共现实体的记忆建立连接 |
| 检索方式 | 实体中心子图探索 + 三元组语义匹配 | 实体匹配 → 命中记忆**加成**，融合进 `score`（与向量+BM25 一并计算） |
| 返回形式 | `relations` 字段（关系列表） | 无单独图负载，只影响排序；`relations` 恒为空列表 |
| 开关 | `enable_graph` + `graph_store` 配置 | **始终开启**，无需配置；`enable_graph` 已废弃（仅为兼容保留，不恢复旧行为） |
| 可用范围 | 研究实现 | Platform 全套餐；**OSS 无**；交互式 Graph 可视化仅 Pro/Enterprise |

**现役 Graph Memory 什么时候有用**：
- 实体中心问题："我们对 Alice 都知道些什么？"→ 把散落在多条记忆里的 Alice 事实连起来
- 多跳召回：一条记忆里的事实连到另一条记忆里的事实
- 成本：零——不用定义 schema、不用标注关系

**旧代码迁移清单**（从外接图库时代升级）：
- [ ] 删除 `graph_store` 配置块与 `enable_graph=True`
- [ ] 业务代码若读取返回中的 `relations` 字段 → 必须改造（现在恒为 `[]`）
- [ ] 依赖"带类型关系"做推理的场景 → 现役共现图**不提供**关系语义，需自行评估
- [ ] OSS 用户需要图能力 → 考虑 Zep Graphiti（开源）或上 Platform
