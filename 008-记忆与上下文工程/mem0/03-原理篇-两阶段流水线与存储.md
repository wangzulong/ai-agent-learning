# 03 - 原理篇：两阶段流水线与存储架构

> 【本节问题】① `add()` 一条消息后 mem0 内部发生了什么？② ADD/UPDATE/DELETE/NOOP 是怎么决定的？③ `search()` 的分数是怎么算出来的？④ 数据存在哪三件套里？

---

## 0. 全景图：一次对话的生命周期

```
你的应用                                mem0 内部
────────                                ─────────────────────────────────────────
add(messages, user_id) ─────┐
                            ▼
              ① 上下文查找（取相关已有记忆）
                            ▼
              ② 事实提取（LLM：消息+摘要+近期消息 → 候选事实）
                            ▼                            ┌─ 异步摘要模块（后台刷新会话摘要）
              ③ 去重 + 向量化                            │
                            ▼                            │
              ④ 更新阶段（LLM 工具调用决策）                │
                 ADD / UPDATE / DELETE / NOOP             │
                            ▼
              ┌────────────────────────────┐
              │ SQL库   │ 向量库  │ 实体存储 │
              └────────────────────────────┘

search(query, filters) ────┐
                           ▼
              查询解析 → 四路信号打分
              语义(向量) + 关键词(BM25) + 实体加成 + 时间意图
                           ▼
              （可选 reranker 精排）→ 排序结果 + score
```

**费曼式理解**：把 mem0 想象成一个档案管理员。
1. 你递给他一页会议记录（add）
2. 他先看看档案柜里已有什么（上下文查找），免得重复立卡
3. 从记录里挑出要点写成卡片草稿（事实提取）
4. 把草稿和相近的旧卡片摆在一起比对（去重 + 更新决策）：
   - 全新的事 → 立新卡（ADD）
   - 补充旧卡的事 → 在旧卡上添内容（UPDATE）
   - 推翻旧卡的事 → 作废旧卡（DELETE）
   - 都是已知信息 → 摇头放下（NOOP）
5. 归档到三个柜子（SQL 存卡片正文、向量库存"意思相近度"、实体存储记"这张卡提到谁"）

## 1. 提取阶段（Extraction Phase）四步拆解

### 第 1 步：上下文查找（Context Lookup）
- **做什么**：用新消息先查一遍已有记忆
- **为什么**：给后续步骤提供"已知信息"参照，避免重复入库
- **输入**：新消息 + **异步摘要模块维护的会话摘要** + 近期消息

### 第 2 步：事实提取（Fact Extraction）
- **做什么**：LLM 从输入中抽取"可复用的持久事实"：偏好、决策、计划、账户信息、持久反馈
- **关键点**：LLM 被指示**忽略寒暄、临时性内容**，只留值得未来复用的
- **输出**：若干候选事实（短句），例如：

```
输入：「我下周要从奥斯汀搬到西雅图，新家想找个离公司近的健身房」
候选事实：
  - User is moving from Austin to Seattle next week
  - User wants a gym near the new home/office
```

**抽取 prompt 的上下文构成（OSS 实现细节）**——LLM 能抽出干净事实、并正确消解代词，靠的是 prompt 里拼了六样东西：

1. **角色**：memory extractor（记忆抽取器）
2. **用户摘要**（user summary）
3. **本次输入的 messages**：注意是整轮完整 messages，不是只抽 user 一句
4. **相关记忆**：把本批消息**展平成字符串** → embedding → 回主库搜相似记忆拼进上下文（帮 LLM 判断"哪些是新信息"）
5. **最近 10 条消息**（来自 SQLite）：专门用来**消解代词**——新消息是 "it is great" / "he's really good at this"，没有前几句就不知道 it / he 指谁，带上前几轮才敢写成"用户更喜欢素食餐厅"这种完整记忆
6. **对话日期 + 当前日期**（时间相关事实的判断依据）

### 第 3 步：去重 + 向量化（Dedup & Embedding）
- **做什么**：合并冗余候选；为每条生成 embedding 存入向量库
- **为什么**：记忆库的价值 = 信噪比。垃圾记忆会让检索命中率崩塌

### 第 4 步：实体提取（Entity Extraction）
- **做什么**：从每条记忆中抽出人名、地名、组织、产品、概念
- **为什么**：① 检索时实体重合可加成；② Platform 上实体直接构成 Graph Memory 的节点（见 04-进阶篇）
- **示例**：上例记忆的实体 = `Austin`、`Seattle`、`gym`

> ⚠️ **重要**：这条流水线是**增量式**的——"搬到西雅图"会作为新事实入库，**旧的"住在奥斯汀"不会被静默改写**。需要修正必须显式 `update`/`delete`，或依赖第 2 阶段的 DELETE 决策。

### 写入的三种模式（add 的三种姿势）

| 模式 | 行为 | 适用 |
|---|---|---|
| **procedural memory**（程序性记忆） | 总结"这轮做了什么过程/用了哪些工具"，便于日后检索并复现同一套流程 | 现在不太常用——社区实践更倾向直接从对话里抽一条 skill |
| **infer=false** | 输入消息直接 embed，**原样入库** | 表结构、法律条款等需要精确原文的内容 |
| **infer=true**（重点/默认姿势） | 触发完整 LLM 抽取管线，从**整轮 messages** 中抽短句事实 | 长期 Agent 的标准做法 |

> 容易误解的点：一个 turn 里既有对话又有 tool call 时，不是"两种方式各存一次"——**从 user 到 final answer 的整段 messages（含 tool_calls 和 tool 结果）作为一份输入**交给 infer=true；tool 过程只当上下文，不会再单独跑一遍 procedural。

## 2. 更新阶段（Update Phase）：四种操作怎么决定

对每条候选事实，mem0 从向量库取 **top-s 相似已有记忆**，让 LLM 通过**工具调用（function calling）**做出决策：

| 操作 | 判定条件 | 例子 |
|---|---|---|
| **ADD** | 语义上全新 | 已知"喜欢篮球" → 新增"开始学钢琴" |
| **UPDATE** | 对已有记忆的补充 | 已知"用户养了一只猫" → "猫叫小黑" |
| **DELETE** | 与已有记忆矛盾 | 已知"用户是素食者" → "我开始吃牛排了" |
| **NOOP** | 重复或无意义信息 | 再次自我介绍姓名 |

**易错点**：DELETE 依赖 LLM 判断矛盾，**不是 100% 可靠**（论文也承认这是局限）。金融、医疗等强一致场景，业务侧要有自己的冲突治理（如版本化 + 人工审核）。

## 3. 检索阶段（Retrieval Phase）：四路信号融合

`search()` 时，mem0 对候选记忆打**融合分**（Platform 上就是返回的那个 `score`）：

| 信号 | 机制 | 擅长 | 例子 |
|---|---|---|---|
| **语义 Semantic** | 向量相似度 | 概念性问题 | "他对吃的有什么讲究" ↔ "花生过敏" |
| **关键词 Keyword** | 词项匹配（BM25） | 精确名字/ID | "订单 A1024 的状态" |
| **实体 Entity** | query 中实体与记忆实体重合 → 加成 | 以人为中心的提问 | "Alice 负责什么" → 所有提到 Alice 的记忆 |
| **时间 Temporal** | 写入时提取的时间元数据 vs query 的时间意图 | 时效性问题 | "他现在住哪"（倾向最新事实） |

- **Platform**：四路全开，实体信号由内置 Graph Memory 驱动（自动、所有套餐可用）
- **OSS**：向量库 + 可选 reranker；实体信号仅做重合加成，**无图记忆**
- **易错点**：`score` 是融合分，直接拿来做"绝对阈值"判断不可靠，按相对排序取 top-k 更稳。

### OSS 检索管线细节（社区源码解析，具体数值随版本可能变化）

**两种触发方式**（后面管线相同，差别只在谁发起 Memory search）：

- **Explicit tool call**：Agent 自己决定调用"搜索记忆"工具
- **Automatic retrieval**：用户消息一发，harness 自动拿消息当 query 检索

**打分流水线**（一个最容易被误解的点：关键词和实体**不能往候选池里加新记忆**，只有 ANN 语义检索负责"出池"）：

1. **embed query**（必须用与建库**同一个 embedding 模型**）→ ANN 召回语义相近记忆；实际召回条数 = **max(topK × 4, 60)**（topK=10 时实际取 60 条候选）
2. **池内并行打分**（只在这 60 条上做）：
   - **关键词分**：query 与记忆都做词形还原（lemma 在写入时就已存），比词重叠（BM25），映射到 0~1
   - **实体加分**：从 query 抽实体 → 实体库命中 → 只保留**已在池内**的记忆，加 0~0.5 分；**实体挂的记忆越少，分越高**——挂 1000 条的 "Paris" 不如只挂 2 条的小众实体相关
3. **三路融合**：语义(0~1) + 关键词(0~1) + 实体(0~0.5) = 满分 **2.5**，相加后 **÷ 2.5** 归一，按最终分取真正的 topK 返回

**query 改写**：mem0 默认**不做** query rewriting；想提升检索，在 **harness 侧**加一层——用户提问先用小 LLM 改写成更好的 query，再送进检索管线。

**定位**：这本质上是一套 RAG（召回→打分→截断），但**不是**"语义检索 ∥ 关键词检索各自召回 → cross-rank"的形态——BM25 和实体加分只在 ANN 池内打分。

## 4. 存储三件套（Where memories live）

| 存储 | 存什么 | 支撑什么查询 | OSS 对应 |
|---|---|---|---|
| **SQL 数据库** | 事实正文 + metadata | 精确取单条、审计 | 默认 SQLite（`~/.mem0/history.db`） |
| **向量数据库** | embeddings | 语义相似 | 默认本地 Qdrant（`/tmp/qdrant`） |
| **实体存储** | 记忆中抽出的实体 | 实体加成；Platform 上支撑图 | OSS 有实体加成，无图 |

**架构特点（面试加分点）**：mem0 **运行时无状态**（服务可水平扩展），**存储层持久**（每个 user_id/agent_id 的记忆跨会话演进）；记忆衰减、摘要等重活**异步**进行，保证检索亚秒级响应。

> **OSS 实现细节 vs 官方文档口径**：在 OSS 里，记忆正文 + 元数据实际存在**主向量库**中，元数据字段相当丰富——创建/更新日期、**归属**（用户侧记忆如"更喜欢素食餐厅"，还是 Agent 侧记忆如学到的时事/流程）、**hash**（只用于**措辞完全相同**的去重，不是最精细的方案）、**词形还原（lemma）版本**（供关键词检索）、**过期日期**、**创建者 attribution**（多 Agent 场景记录是哪一个写的）；实体抽出到**实体向量库**并链回主记忆（问"巴黎"→ 先命中实体 Paris → 带回链上的全部主记忆）。而 **SQLite** 承担两件并列的事：① 增删改**变更日志**（对账、回放、溯源"这条记忆怎么来的"）；② 保存**最近 10 条消息**给抽取器消解代词。两种口径不矛盾：Platform 把事实+元数据的 source of truth 收敛到 SQL 层；OSS 是"向量库为主、SQLite 记账"。

## 5. 伪代码：把两阶段写出来（理解用，非真实源码）

```python
# ========== add() 内部（简化伪代码） ==========
def add(messages, user_id, ...):
    summary = get_or_refresh_summary(user_id)        # 异步摘要模块
    related = vector_search(messages, user_id)       # ① 上下文查找
    candidates = llm_extract(messages, summary, related)  # ② 事实提取
    candidates = dedup(candidates)                   # ③ 去重
    for fact in candidates:
        emb = embed(fact)
        similar = vector_topk(emb, s)                # 取 top-s 相似记忆
        op = llm_decide(fact, similar)               # ④ 更新决策（工具调用）
        if op == ADD:    insert_sql(fact); vector_upsert(emb)
        if op == UPDATE: merge_and_rewrite(similar[0], fact)
        if op == DELETE: mark_deleted(similar[0])
        if op == NOOP:   pass
    entities = llm_extract_entities(candidates)      # 实体提取 → 实体存储
    async_refresh_summary(user_id)                   # 摘要后台刷新

# ========== search() 内部（简化伪代码） ==========
def search(query, filters, limit=10):
    q_emb = embed(query)
    cands = vector_search(q_emb, filters)            # 语义召回
    scores = fuse(
        semantic = cosine(q_emb, cands),
        keyword  = bm25(query, cands),
        entity   = entity_overlap(query, cands),     # Platform: 图加成
        temporal = time_intent(query, cands),
    )
    return rerank_topk(cands, scores, limit)         # 可选精排
```
