# 02 - 概念篇：核心概念精讲（12 张概念卡片）

> 【本节问题】① 记忆四层分别是什么、什么时候用？② user_id/agent_id/run_id 有什么区别？③ "消息"和"记忆"差在哪？④ 一条记忆对象长什么样？

---

**每张卡片的读法**：【一句话人话】→【类比】→【展开】→【易错点】。第一遍只看前两层，第二遍再看展开。

---

### 卡片 1：记忆层（Memory Layer）

- **一句话人话**：专门给 Agent 管"记什么、怎么记、怎么想起来"的基础设施。
- **类比**：Agent 是一个每天失忆的天才员工，记忆层是给他配的档案室 + 档案管理员。
- **展开**：独立于 Agent 框架的一层，对上提供 `add/search/update/delete` API，对下管理向量库、SQL、实体存储。应用只管调 API，不用操心存哪、怎么检索。
- **易错点**：记忆层 ≠ Agent 框架 ≠ RAG 框架。mem0 只管记忆，编排、工具、路由一概不管。

### 卡片 2：事实提取（Fact Extraction）

- **一句话人话**：从对话里挑出"值得长期记住的事"，写成干净的短句。
- **类比**：会议纪要员——不逐字记录，只把"决议、承诺、偏好"提炼成条目。
- **展开**：mem0 用 LLM 做提取。"我喜欢靠过道的座位" → 存成 `User prefers aisle seats`。默认开启（infer 模式）；也可关闭存原文。
- **易错点**：提取是**有损压缩**，所以重要原文要用 `infer=False` 保真。

### 卡片 3：四层记忆（Memory Types）

- **一句话人话**：便签（本轮）→ 日志（本次会话）→ 档案（这个用户）→ 图书馆（全公司）。
- **类比**：见上，范围逐层扩大、寿命逐层变长。
- **展开**：

| 层 | 生命周期 | 典型内容 | 怎么用 |
|---|---|---|---|
| Conversation | 单轮 | 工具输出、中间推理 | 不入长期库，轮次结束即弃 |
| Session | 分钟~小时 | onboarding 流程状态 | 挂 `run_id`，结束自动过期 |
| User | 数周~永久 | 偏好、账户信息 | 挂 `user_id`，跨会话个性化 |
| Org | 全局 | FAQ、产品目录、政策 | 多 Agent 共享，需维护者 |

- **易错点**：别把"本轮工具输出"这种一次性信息存进 user 层——记忆层最怕垃圾越积越多。

### 卡片 4：作用域三剑客（user_id / agent_id / run_id）

- **一句话人话**：给记忆贴的三种"归属标签"——记在谁名下、哪个 Agent 名下、哪次任务名下。
- **类比**：图书档案的"借阅人 / 部门 / 借阅批次"三联单。
- **展开**：
  - `user_id`：长期个性化，最常用
  - `agent_id`：同一个用户下，不同 Agent 各有记忆空间（又可通过共享 user 记忆互通）
  - `run_id`：**短期任务上下文，靠它实现"自动过期"**——文档原话：想自动过期就用 run_id
- **易错点**：检索时**必须带作用域 filter**，否则不同用户/Agent 的记忆会串味（数据泄漏事故高发点！）。

### 卡片 5：消息 vs 记忆（Messages vs Memories）

- **一句话人话**：你发进去的是聊天记录，存下来的不是聊天记录，而是提炼后的事实卡片。
- **类比**：上课听的是老师两小时讲话（消息），笔记本上留的是十行要点（记忆）。
- **展开**：

| 输入消息 | 存储的记忆 |
|---|---|
| "我喜欢靠过道的座位" | `User prefers aisle seats` |
| "这个项目用 Postgres 吧" | `Project decision: use Postgres` |

- **易错点**：原样入库会污染检索（寒暄、口语、重复全在里面）。除非确需原文，保持 infer 开启。

### 卡片 6：infer 参数（提取开关）

- **一句话人话**：`infer=True`（默认）让 LLM 提炼后存；`infer=False` 一字不改存原文。
- **类比**：笔记员速记 vs 录音笔原样保留。
- **展开**：适合 `infer=False` 的场景——法律条款原文、配置片段、需要精确引用的内容。
- **易错点**：两种模式混用时注意：原文记忆不会被去重合并逻辑整理，会越积越多。

### 卡片 7：记忆对象（Memory Object）

- **一句话人话**：每条记忆不是一行向量，而是一个有身份证、有分数、有出生日期的完整对象。
- **类比**：档案卡片 = 正文 + 标签 + 检索号 + 归档时间。
- **展开**（真实返回结构）：

```json
{
  "id": "mem_123abc",                  // 身份证：update/delete/history 都靠它
  "memory": "Name is Alex. Enjoys basketball and gaming.",
  "user_id": "alex",
  "categories": ["personal_info"],     // 分类标签
  "created_at": "2025-10-22T04:40:22Z",
  "score": 0.89                         // 检索相关度分（四路信号融合的结果）
}
```

- **易错点**：`score` 是融合分，不是纯余弦相似度；不要自己再按 0.5 之类的阈值粗暴截断而忽略排序。

### 卡片 8：CRUD 与记忆生命周期

- **一句话人话**：记忆不是只增不减的，而是像数据库记录一样可增、可改、可删、可查历史。
- **类比**：档案卡片可以新立（ADD）、补充（UPDATE）、作废（DELETE），每次操作都有登记（history）。
- **展开**：`add / search / get_all / get / update / delete / delete_all / history / reset`（详见 05-实战篇）。
- **易错点**：`update/delete` 需要先拿到 `memory_id`——通常从 `search` 或 `get_all` 的结果里取。

### 卡片 9：自动提取是"增量式"的（不会静默改写）

- **一句话人话**：用户改主意了，mem0 会**追加新事实**，但不会偷偷把旧记忆改掉。
- **类比**：档案管理员把新声明归档，但不动旧档案——改不改由你决定。
- **展开**：用户说"我从奥斯汀搬到了西雅图"，新事实入库，旧事实仍在。需要修正 → 显式 `update/delete`；或依赖更新阶段的 DELETE 决策（见 03-原理篇）。
- **易错点**：以为 mem0 自动维护一致性而从不清理 → 检索可能同时召回新旧矛盾记忆。生产上要有治理策略。

### 卡片 10：metadata 与多租户（Multi-tenant）

- **一句话人话**：除了三剑客，你还能给记忆贴任意自定义标签，检索时按标签过滤。
- **类比**：档案卡上的自定义角标："华东区"、"售后业务"。
- **展开**：典型用法——workspace、tenant、产品线、数据来源。生产上强烈建议显式规划，而非事后补。
- **易错点**：metadata 是精确过滤（filter），不是语义检索条件；"语义找相似 + filter 圈范围"要配合使用。

### 卡片 11：异步摘要（Asynchronous Summary）

- **一句话人话**：mem0 在后台持续维护一份"会话摘要"，供下一次提取时当上下文用。
- **类比**：会议每半小时，助理更新一页"当前进展"贴在白板上。
- **展开**：论文中的异步摘要生成模块——提取新事实时，携带最新摘要能判断"这条是不是新信息"。摘要异步进行，不阻塞主链路。
- **易错点**：这是内部机制，你感知不到，但它是"提取质量"的关键保障——摘要过期会漏提/误判。

### 卡片 12：Reranker（重排序器）

- **一句话人话**：向量检索粗排出一批候选后，请一个更精细的裁判把最相关的排到前面。
- **类比**：初筛（向量，快而糙）→ 复审（reranker，慢而准）。
- **展开**：OSS 默认不启用；可配 Cohere 等 provider。官方建议 `top_k` 10~20。
- **易错点**：数据量小时收益不明显；先量检索命中率，再决定要不要加。
