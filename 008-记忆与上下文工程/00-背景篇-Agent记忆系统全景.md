## 1. 为什么从认知科学讲起（费曼式铺垫）

给 Agent 设计记忆，本质是在**模仿人类大脑的记忆管理**。先花 3 分钟了解人类记忆，后面所有概念都有锚点。

**类比：把大脑想象成一家公司**
- 前台（感觉记忆）：所有信息先经过这里，只停留几秒，99% 直接扔掉
- 工位便签（工作记忆/短期记忆）：正在处理的几件事，容量极小（心理学经典结论：约 7±2 个组块），关机就没了
- 档案室（长期记忆）：分三个柜子——
  - **情景记忆**（episodic）：发生过的事。"上周三和张总开了会"
  - **语义记忆**（semantic）：事实与知识。"张总是客户方的技术负责人"
  - **程序记忆**（procedural）："怎么做"的技能，比如骑车、写周报的流程
- 遗忘曲线（艾宾浩斯）：不复习的记忆按指数衰减 → 启发：Agent 记忆也需要**衰减/淘汰机制**，否则垃圾越堆越多

## 2. 映射到 AI Agent：记忆分类学

| 人类记忆 | Agent 对应物 | 典型实现 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 上下文窗口内的对话历史、scratchpad | 直接放 prompt | 单次会话 |
| 情景记忆 | 过往交互的摘要、事件日志 | 对话总结库 | 跨会话 |
| 语义记忆 | 用户画像、领域事实、知识 | 向量库/知识图谱 | 跨会话、长期 |
| 程序记忆 | Agent 学到的操作模式、技能流程 | 技能库、few-shot 模板 | 长期 |

另一条常用的切分维度：

```
Agent 记忆
├── 短期记忆（Short-term）
│   ├── 对话历史（conversation history）
│   ├── 工作状态（工具输出、中间变量）
│   └── 注意上下文（当前任务的焦点）
└── 长期记忆（Long-term）
    ├── 事实型（用户偏好、账户信息）        ← mem0 的主战场
    ├── 情节型（过去任务的总结）
    ├── 语义型（概念关系、知识图谱）
    └── 程序型（"怎么做"的模式）
```

### 2.1 关键区分：会话记忆 vs 长期记忆

这是初学者最容易混的一对概念，用 harness（Agent 脚手架）视角讲最清楚：

- **LLM 本身是无状态的**：每次调用独立，第 2 次调用看不到第 1 次的 prompt 和回复
- **会话记忆**其实是 harness 在维护：每轮结束后把 user 消息和回复**追加进 history**，下一轮**整段重发**给 LLM——状态在 harness 里，不在模型里
- 但这只在**同一段会话**内有效；新开会话，上一段内容不可达 → 跨会话失忆
- **长期记忆** = 挂在会话**外面**的独立存储：从每一段对话里沉淀事实、每一轮检索使用、跨会话持久。**务必与会话存储分开**（不同文件/不同 store）
- 以用户为中心的记忆可**跨 Agent 共享**：你的偏好可以同时被 ChatGPT、Claude 等不同 Agent 使用
- 生效方式两条路：给 Agent"搜记忆"的工具（explicit tool call），或每轮自动读写（automatic retrieval）

## 3. 记忆层在 Agent 架构中的位置（上下文工程视角）

**2024 年后业内形成共识：Agent 的核心工程问题是"上下文工程"（Context Engineering）**——在有限的上下文窗口里，决定"放什么、不放什么、以什么形式放"。一次 Agent 请求的上下文通常由五部分拼成：

```
┌─────────────────────────────────────────┐
│              模型上下文窗口               │
├─────────────────────────────────────────┤
│ ① System Prompt（角色/规则/工具说明）      │ ← 相对静态
│ ② 检索到的知识（RAG：文档/知识库片段）      │ ← 静态知识
│ ③ 记忆（Memories：这个用户/任务的历史事实） │ ← 动态、个性化 ★记忆层负责
│ ④ 当前对话（本轮 user 消息 + 近期历史）     │
│ ⑤ 工具调用结果（实时数据）                 │
└─────────────────────────────────────────┘
```

**关键区分：RAG ≠ 记忆**
- RAG 管**知识**：静态的、对所有人一样的语料（产品手册、政策文档）
- 记忆层管**经历**：动态的、属于具体用户/会话的事实沉淀（"这个用户对花生过敏"）
- 生产系统两者叠加使用（详见 mem0/06-生产篇）

## 4. 为什么需要专门的"记忆层"（三个反面方案）

| 反面方案 | 做法 | 死因 |
|---|---|---|
| A. 全量上下文 | 把所有历史塞进 prompt | ① 超窗口；② 成本随历史线性涨；③ 延迟爆炸（见 01-问题篇的账本） |
| B. 手工画像 | 自己设计 schema 存用户偏好 | 结构死板、只适合结构化事实，难以承载开放式对话沉淀；每个 Agent 重复造轮子 |
| C. 简单摘要 | 每轮让 LLM 总结历史 | 摘要丢细节、无法精确检索单条事实、越摘越长 |

**记忆层的价值主张**：把"记忆管理"（提取→存储→检索→更新→遗忘）封装成独立基础设施，像数据库之于应用一样，让 Agent 框架只管推理。

## 5. 学术与工程脉络（读论文前的地图）

```
2023.10  MemGPT (arXiv 2310.08560)
         把 LLM 当操作系统，记忆分页管理 → 后发展为 Letta 平台
   │
2024     LoCoMo 基准发布
         长对话记忆评测数据集（10 段超长对话 × ~200 问）→ 后续所有记忆方案的比赛场
   │
2024     HippoRAG（神经生物学启发）/ A-Mem（自组织记忆）/ LangMem（LangChain 生态）
         各种记忆机制百花齐放
   │
2025.04  Mem0 论文 (arXiv 2504.19413)  ★本专题主案例
         两阶段管线（提取+更新），主打"生产就绪"：精度接近全量上下文，
         延迟降 91%、token 省 90%
   │
2025+    Zep Graphiti（时序知识图谱）、各家商业化平台成熟
   │
2026     竞争焦点转向：多模态记忆、记忆治理（合规/审计）、压缩引擎、评测标准
```

**读文献的建议顺序**：先用 mem0（工程上手最友好）→ 再读 MemGPT 理解"操作系统式"思路 → 最后读 Zep/Graphiti 理解图谱路线。
