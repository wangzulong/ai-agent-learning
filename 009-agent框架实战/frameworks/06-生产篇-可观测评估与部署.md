# 06 · 生产篇：可观测、评估与部署

> 【本节问题】① Agent 的 trace 怎么看、接哪个平台？② 框架自带的评估能力和 006 篇评估集纪律怎么结合？③ LangGraph 应用有哪些部署形态，怎么选？④ 版本升级有哪些已知的坑？

## 1. 可观测：trace 是 Agent 的事故现场

**【一句话人话】** 生产上 Agent 出问题，你唯一能依赖的就是 trace——它记录每次执行每一步的输入、输出、token、耗时。

**【生活类比】** 生产事故回查 = 查网关 access log + 应用 log + DB 慢查询三件套；Agent 的 trace = 这三件套合体的"时间旅行录像带"。

### 1.1 平台选型

| 平台 | 特点 | 适合 |
|---|---|---|
| LangSmith | LangChain 同门，trace + 评估 + 数据集 + 部署一体化，商业 SaaS | 已用 LangGraph 全家桶 |
| Langfuse | 开源可自托管，OTel 兼容，trace + eval + prompt 管理 | 数据不出内网（贸易公司常见合规要求） |
| OTel 直连 | 标准协议，接 Datadog/SkyWalking/Jaeger | 已有 APM 体系的企业 |

> LangGraph 每个节点执行天然是一个 span（03 原理篇第 5 层），接 LangSmith 只需设 `LANGSMITH_TRACING=true` + API key；接 Langfuse 用其 LangGraph callback 集成。CTRM 建议：**客户报盘数据涉密，优先 Langfuse 自托管**。

### 1.2 CTRM 的 trace 实践清单

1. **thread_id 进 trace 元数据**：报盘单号 PB-2026-001 能直接搜到完整链路——审计合规刚需。
2. **关键节点打业务标签**：router 结果、建议单价格带内外，作为 trace 的 tag，便于聚合统计"越限价带单占比"。
3. **token 成本按业务线分摊**：点价/套保/咨询分 namespace 记账。
4. **告警**：单次执行 span 数突增 = 疑似循环失控；interrupt 挂起超 24h = 审批积压。

## 2. 评估：框架 eval + 006 评估集纪律

框架给你**评估工具**，006 篇给你**评估纪律**——两者结合才有效。

### 2.1 LangGraph 侧的评估抓手

- **LangSmith Datasets**：把评估集（输入 → 期望）存为数据集，跑实验对比 prompt/模型版本，自动打分。
- **Langfuse Evals**：同样支持数据集 + LLM-as-judge + 人工标注队列。
- **单节点测试**：LangGraph 节点是普通函数——`extract_node` 可以不启动整图直接单测（框架化带来的可测性红利，01 问题篇）。
- **time-travel 回归**：改了 prompt 后从历史 checkpoint 分叉重跑，对比新旧结果——这是 checkpointer 附赠的独特评估手段。

### 2.2 与 006 篇纪律的结合

| 006 篇纪律 | 在框架下的落地 |
|---|---|
| 评估集进版本库、与代码同评审 | 数据集导出 JSON 入 git；LangSmith/Langfuse 只做执行载体 |
| 线上样本回流 | trace 按规则筛（如人工否决的单）自动进评估集候选池 |
| 分层指标 | 节点级（抽取准确率）/ 全链路级（建议单采纳率）/ 成本级（token/单） |
| 禁止线上直接试错 | 用数据集 + 实验（experiment）对比，胜出才发布 |

> 优先级要点：先建"抽取准确率"这一个指标并持续积累（成本最低、价值最高），再扩全链路指标。

## 3. 部署：三种形态

**【一句话人话】** Agent 服务的特殊之处：它有状态（checkpointer）、有长挂起（interrupt），部署方案必须先回答"状态放哪、挂起谁兜底"。

### 3.1 形态对比

| 形态 | 是什么 | 适用 |
|---|---|---|
| LangGraph Server / LangSmith Deployment | 官方托管/企业部署：自带持久化队列、Cron、双写 API（来源：LangChain 融资公告，原 LangGraph Platform 并入 LangSmith 部署） | 想最快上线、接受 SaaS 或私有化报价 |
| 自托管 `langgraph-cli` / `langgraph dev` 容器化 | 官方开源 server 镜像打进自己的 K8s，Postgres 自管 | 数据合规、运维自主 |
| 作为库嵌入 FastAPI | `graph` 对象直接在自家 Python 服务里跑 | 只需轻并发、想复用已有服务框架 |

### 3.2 CTRM 推荐架构

```
Vue 2.7 前端 ──SSE──> Java CTRM 主系统 ──REST──> Python Agent 服务(FastAPI 嵌入 graph)
                                                    ├─ PostgresSaver（状态/挂起）
                                                    └─ Langfuse 自托管（trace）
```

- Agent 服务无状态化：进程可随时重启，挂起的单在 Postgres 里——**这是 04/05 篇持久化件在生产架构里的兑现**。
- 人审闭环：Java 侧审批通过后调 Python 的 resume 接口（05 实战篇 2.8 的 `Command(resume=...)` 包成 REST）。
- 发布策略：评估实验胜出的 prompt/图定义作为版本化配置发布，回滚 = 切回上一版本配置。

## 4. 版本升级坑

1. **LangChain 1.0 断代**：2025-10-22 起 `langgraph.prebuilt` 弃用，功能迁入 `langchain.agents`；官方承诺 1.x 内无破坏性变更（来源：aiwiki.ai / LangChain 博客）。升级前先查弃用清单。
2. **锁版本**：Spring AI 曾在小版本间破坏 API（fast.io 2026 指出须显式 pin 版本）；Python 侧同样建议 lock（uv/pip-tools），LangGraph 1.2.x 的命令式 API 等（DeltaChannel）只在最新 minor。
3. **checkpoint 序列化兼容**：升级可能改状态序列化格式——升级前确认 checkpointer 后端兼容矩阵，跨大版本升级先在新环境回放历史 thread 验证。
4. **模型 API 变动**：`init_chat_model` 隔离了部分变动，但 provider 侧（如工具调用参数格式）仍可能波及，评估集回归是安全网。
