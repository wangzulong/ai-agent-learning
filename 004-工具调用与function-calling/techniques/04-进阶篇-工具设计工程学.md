## 1. 第一性原理：工具定义就是 prompt

模型选工具靠的不是魔法，是**注意力**：tools 数组随每次请求进上下文，description 和参数描述就是模型"读到的文档"。所以——

**一句话人话**：写工具定义 = 给一个聪明但没上过班的实习生写《操作手册》，你漏写的每一个细节，他都会用一个你不想要的默认行为补上。

**工程推论**：工具定义要进版本管理、要走 code review、要配评估——和 001 篇的提示词完全同构。

## 2. 描述工程：写"何时用/何时不用"

| 要素 | 反例（常见废柴描述） | 正例 |
|---|---|---|
| 一句话职责 | `"查询数据"` | `"按品种查询当前可用库存，返回可用量与仓库列表"` |
| 何时用 | （没写） | `"需要确认某品种现货库存时调用"` |
| **何时不用** | （没写） | `"不要用它查期货价格——那用 query_futures_price"` |
| 返回承诺 | （没写） | `"返回 JSON：variety/available_tons/warehouses[]；品种无效时返回 available_varieties"` |
| 失败语义 | （没写） | `"查询失败返回 error 字段，不要重试超过 1 次"` |

**"何时不用"是被绝大多数人忽略的黄金栏位**——工具选择错误的两大来源之一就是边界模糊（另一个是名字歧义）。

## 3. 参数设计：少而精五原则

1. **扁平化**：嵌套对象是模型出错重灾区，能一层就一层（OpenAI 官方指南同款建议）
2. **枚举约束**：取值有限就上 `enum`（品种 `["M","RM","Y"]`），把"自由发挥空间"压缩到零
3. **required 精准**：必填项过多会让模型编造，过多缺省让模型乱猜——只把"缺了就没法执行"的设为 required
4. **描述写单位与格式**：`"基差（元/吨），如 -80"` 比 `"基差"` 少一半幻觉
5. **禁用自由文本传结构**：别让模型往一个 string 参数里塞 JSON——需要结构就给结构参数

## 4. 返回值工程：token 是预算

| 场景 | 不好的返回 | 好的返回 |
|---|---|---|
| 列表查询 | 全表 500 行 JSON（≈30k token） | 默认 top20 + `page` 参数；摘要行数 |
| 行情查询 | 全字段 tick 数据 | 只回模型需要的：合约/最新价/基差/时间戳 |
| 错误信息 | `"Error: -1"` | `"品种 'M9' 不存在。可用品种：M, RM, Y"`（可自纠） |
| 大文本 | 原文全文 | 截断 + `"前 2000 字符，如需继续传 offset"` |

**为什么**：返回值全部进上下文，一次 30k 的返回不仅贵，还会**稀释**后续指令的注意力（context rot，001/003 篇）。工具返回要像 API 分页一样设计——**给模型的返回 = 人读的 API 返回的摘要投影**。

## 5. 读写分级与幂等（生产硬要求）

- **读写分级**：工具标注只读/写；只读可自动重试、可并行；写操作必须幂等（带客户端生成的 request_id）或挂起人工确认（003 篇分级自主）
- **幂等**：网络重试是常态，`create_price_apply` 重试两次 = 建三张单就是事故。方案：request_id 去重表（MySQL 一行搞定，Java 开发者秒懂）
- **时间参数显式化**：别让模型"猜当前时间"——把当前日期作为参数传进去，或工具返回里带服务端时间

## 6. 工具数量与选择准确率

经验规律（BFCL 榜单与各家指南共识）：**10 个以内几乎不受影响；20+ 开始明显混淆；50+ 必须做命名空间/动态加载**。缓解手段：

- 前缀分组：`inventory_query` / `inventory_lock` / `pricing_query`（名字本身当命名空间）
- 动态工具注入：按任务阶段只挂当阶段工具（路由后挂子集）
- 工具检索：工具库上百时，先检索相关工具再挂载（工具的 RAG）
