# 03 · 原理篇：协作模式与通信解剖

> 【本节问题】① Agent 之间一次协作的完整数据流长什么样？② 消息里到底该传什么——完整历史、摘要还是结构化产物？③ "怎么传"有哪几条通道，各适合什么场景？④ 上下文隔离为什么是多 Agent 的第一性收益，它和 context rot 什么关系？

## 1. 一次协作的解剖：五段数据流

以点价评审为例，一笔任务从进到出的完整数据流：

```
用户请求（点价单评审）
   │ ①任务接收
   ▼
主管 Agent：解析 → 拆解为 3 个子任务 → 生成 3 份 handoff 消息
   │ ②派发（并行）
   ▼
抽取员 / 风控员 / 定价员：各自带最小上下文独立执行（工具循环照旧）
   │ ③回传（产物）
   ▼
三份结构化交付物（extraction.json / risk.json / pricing.json）
   │ ④汇总校验
   ▼
主管：Schema 校验 → 交叉核对（数量口径、价格依据）→ 生成评审意见
   │ ⑤交付
   ▼
review.json → 人工复核 → 归档 CTRM
```

对 Java 开发者，这就是一次**扇出-扇入（scatter-gather）**：`CompletableFuture.allOf` 派发、各服务返回 DTO、网关聚合校验。唯一区别是"服务"换成了带 Prompt 与工具循环的 Agent。

## 2. 传什么：三种载荷的取舍

| 载荷形态 | 内容 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 完整历史 | 把 A 的对话/工具日志全量给 B | 信息零损失 | Token 爆炸；把 B 拖进 context rot | 强耦合接续（B 必须复现 A 的推理） |
| 摘要 | A 用自然语言压缩工作结果 | 便宜、聚焦 | 压缩丢细节，关键数字可能被"大概化" | 松耦合咨询（B 只要结论） |
| 结构化产物 | 约定 Schema 的 JSON 交付物 | 机器可校验、口径统一、可入库 | 前期要设计 Schema | 生产系统默认选择 |

**生产默认：结构化产物**。点价评审中主管给风控员的不是"合同全文和历史"，而是抽取员产出的 `extraction.json`——风控员需要的字段就在里面，一行不多。

优先级要点：
1. 子任务间传**结构化产物**，别传聊天记录；
2. 需要"再加工"的场景传**摘要**，但数字必须原文保留（禁止模型四舍五入金额）；
3. **完整历史**只留给"接手未完成任务"（如 handoff 换人重试），且要配截断策略。

## 3. 怎么传：三条通道

| 通道 | 机制 | 类比 | 适用 |
|---|---|---|---|
| 进程内直接调用 | 函数/SDK 调用，共享内存对象 | 同 JVM 内方法调用 | 同一编排进程内的 Worker（05-实战篇走这条） |
| 共享存储黑板 | Redis/DB/文件作为公共空间 | 共享缓存表 | 异步协作、多方共享事实 |
| A2A 网络调用 | HTTP + Agent Card 发现 + Task 生命周期 | 微服务 RPC + 服务注册发现 | 跨进程、跨团队、跨厂商 Agent |

经验法则（社区共识，Alice Labs 2026 实践综述）：**"A2A between crews, agents-as-tools inside a crew"**——同一进程内的 Agent 别走 HTTP，把对方当工具直接调；跨边界（跨服务/跨组织）才上 A2A。

## 4. 上下文隔离：多 Agent 的第一性收益

【一句话人话】上下文隔离 = **每个 SubAgent 只带自己那部分上下文**：主管不发全文，只发该子任务需要的最小集合。
【生活类比】给专员派活只给相关材料，而不是把整个档案室搬到他桌上。

为什么这是第一性收益：

1. **对抗 context rot**（003）：上下文越长，注意力越稀释。风控员的窗口里只有合同 + 授信数据，没有行情噪声，关键信息不被冲淡；
2. **省 Token**：不重复给每个 Worker 发全量资料；
3. **降干扰**：抽取的"逐字引用"与定价的"合理推断"两种 Prompt 风格不再互相污染；
4. **可并行**：隔离是并行的前提——不共享可变状态，才能放心 `gather`。

**隔离的反面是口径漂移**：三个 Worker 各自为政后，"数量"可能被抽成吨、被风控读成手数。所以隔离必须配**共享契约**——交付物 Schema 与公共事实字典（见 06-生产篇防御①）。

## 5. 协作模式的三个层次（由简到繁）

| 层次 | 形态 | 主管职责 | 适用 |
|---|---|---|---|
| L1 固定委派 | 子任务预先写死，主管只派发与汇总 | 派活 + 校验 | 流程确定的评审/审核类 |
| L2 动态拆解 | 主管 LLM 自行决定拆几个、拆成啥 | 规划 + 编排 | 开放任务（研究、巡检） |
| L3 自主协作 | Worker 间可直接通信、互派任务 | 定规则 + 仲裁 | 对等辩论、复杂协商 |

优先级要点：**生产从 L1 起步**——L2 已经引入"拆解错误"风险，L3 的协调成本（O(n²) 通信）与死循环风险只值得在确需"辩论"的场景支付。点价评审用 L1：拆解逻辑写死在代码里，主管 LLM 只负责汇总校验，这是 05-实战篇的取向。

## 【本节自测】

1. **一次多 Agent 协作的五段数据流？** 要点：接收 → 拆解派发 → 并行执行 → 回传产物 → 汇总校验交付（scatter-gather）。
2. **三种载荷怎么选？** 要点：默认结构化产物；松耦合咨询用摘要（数字原文保留）；完整历史仅用于接手重试且配截断。
3. **三条通道各对应什么 Java 类比？** 要点：进程内调用 ≈ 同 JVM 方法调用；共享黑板 ≈ 共享缓存；A2A ≈ RPC + 服务发现。
4. **"A2A between crews, agents-as-tools inside a crew"什么意思？** 要点：进程内直接调，跨边界才走协议，别为同进程 Agent 加 HTTP 跳数。
5. **上下文隔离的四个收益？** 要点：对抗 context rot、省 Token、降风格干扰、可并行。
6. **隔离带来的新风险是什么、怎么补？** 要点：口径漂移；用共享交付物 Schema + 公共事实字典对齐。
7. **三个协作层次，生产该从哪层起步？** 要点：L1 固定委派起步；L2/L3 各自的风险与适用。
