# 07 · 对比篇：框架与拓扑选型

> 【本节问题】① 拓扑怎么选，有没有可直接照走的决策树？② 主流多 Agent 框架各是什么定位，怎么选？③ 什么时候应该**坚持单 Agent**，谁有资格拍板？④ 这些框架和 009 篇怎么衔接？

## 1. 拓扑选型决策树

```
任务能否分解出边界清晰的独立子任务？
├─ 否 ──→ 坚持单 Agent（先优化 Prompt/工具/上下文压缩）
└─ 是 ──→ 子任务间有先后依赖（SOP 固定）？
          ├─ 是 ──→ 流水线（抽取→清洗→审核→归档）
          └─ 否 ──→ 子任务结果需要汇总为单一结论？
                    ├─ 是 ──→ 星型（主管 + Worker）★ 默认首选
                    │         └─ 子任务规模大到一层拆不动？→ 层级（递归分治）
                    └─ 否 ──→ 真需要多方辩论/交叉审议？
                              ├─ 是 ──→ 网状（必须配轮次上限 + 仲裁者）
                              └─ 否 ──→ 回到上一级重新审视（多半是星型）
```

口诀回顾（配 007-04）：**能流水线就流水线，要汇总用星型，大到拆不动用层级，真要辩论才上网状。**
点价评审走"是分解 → 无依赖 → 要汇总"分支 = **星型**。

## 2. 框架对比表（2026-09）

| 框架 | 核心抽象 | 强项 | 弱项 | 适用 | 现状注记 |
|---|---|---|---|---|---|
| **LangGraph** | StateGraph 状态图 | 图编排可控、checkpoint、HITL 原生（interrupt）、LangSmith 观测成熟 | 学习曲线陡 | 企业生产、需审计与人工卡点 | 有测评称其 Token 效率比 CrewAI 高 15~18%（app-lab.ai 2026 综述引 shipsquad benchmark，非官方） |
| **OpenAI Agents SDK** | Agent + handoff 原语 | 极简 API、免费内置 Tracing、guardrails | 偏 OpenAI 生态 | OpenAI 栈团队、客服路由、快速起步 | Swarm 的生产化继任 |
| **CrewAI** | crew + role/task | 角色隐喻直观、20 分钟上手、已原生支持 A2A | 灵活性较低 | 原型、内容/数据流水线 | A2A 支持见 trendix 2026 报道 |
| **AutoGen / AG2** | group chat 对话协作 | 多 Agent 辩论研究渊源深 | 配置复杂；有社区报道称 AutoGen 转入维护模式 | 辩论/验证类实验 | **截至 2026-09 未见微软官方文档宣布 EOL**；新项目社区建议 MAF 或 AG2 |
| **Microsoft Agent Framework** | Python + .NET 双栈 | Azure 集成、企业治理、A2A GA | 微软生态绑定 | .NET 企业、Azure 客户 | 融合 AutoGen 与 Semantic Kernel 的官方新框架 |
| **Claude Managed Agents** | 云托管多 Agent | 免运维 | Anthropic 依赖 | 已在 Claude 栈、不想管基础设施 | 2026 年新发布的托管形态 |
| **手写（05 篇）** | 代码即框架 | 零魔法、完全可控、教学价值最高 | 无checkpoint/重试等基建 | 学习原理、超简单场景 | 本章实战篇即此路线 |

选型三原则：
1. **别按 GitHub 星数选**（多来源测评共识）——按"控制粒度需求 + 现有技术栈 + 可观测成熟度"选；
2. **先框架后自研**：原型期用框架快速验证，框架成为硬约束时再抽关键件自研；
3. **评测基建比框架重要**：框架差异 < 模型选择 + 评测体系（DeepEval 等）+ 人工卡点设计的影响。

## 3. "什么时候坚持单 Agent"裁定

裁定优先级（从上往下，命中任何一条就**不上**多 Agent）：

1. **规则可穷举**：步骤固定、无歧义 → 写代码/工作流引擎（Camunda 都比 Agent 便宜）；
2. **一次问答能解决**：单轮 + 少量工具调用搞定 → 单 Agent；
3. **子任务强耦合**：下游需要上游完整推理链 → 隔离反而制造断层；
4. **Token 预算 < 收益**：15 倍溢价买不回等值的时间/质量提升；
5. **合规要求全程单点可解释**：多 Agent 过程回放成本高于业务价值时。

反面裁定（满足 2 条以上，**该上**）：可分解、可并行、需不同专长/工具、上下文装不下、需交叉验证（见 01-问题篇信号清单）。

**点价评审的最终裁定**：满足 4 条该上信号（可分解/可并行/专长不同/需交叉验证），且是高风险高频核心流程，Token 溢价有业务价值兜底 → 上多 Agent，拓扑取星型，框架建议 LangGraph（需审计与 HITL）起步；评审链路固化后可降级为流水线 + 局部 Agent 的混合形态。

## 【本节自测】

1. **拓扑决策树的第一问是什么？** 要点："能否分解出边界清晰的独立子任务"——不能就坚持单 Agent。
2. **五种路线（含手写）各自的适用一句话？** 要点：LangGraph 企业可控；OpenAI SDK 轻量快速；CrewAI 快速原型；MAF Azure 企业；手写学与极简。
3. **AutoGen 的现状怎么表述才严谨？** 要点：有社区报道称转入维护模式，截至 2026-09 未见微软官方 EOL 宣告；新项目多建议 MAF/AG2。
4. **坚持单 Agent 的五条裁定？** 要点：规则可穷举、一次问答可解、强耦合、Token 不划算、单点可解释合规。
5. **选型三原则？** 要点：不按星数选；先框架后自研；评测基建比框架更重要。
6. **点价评审的完整裁定链？** 要点：4 条该上信号 → 星型 → LangGraph 起步 → 流程固化后可降级混合形态。
7. **CrewAI 在协议层面的亮点？** 要点：已原生支持 A2A，适合跨框架协作场景的原型验证。
