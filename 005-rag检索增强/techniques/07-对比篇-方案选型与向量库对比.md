# 07-对比篇：方案选型与向量库对比

> 【本节问题】① 五个主流向量库怎么选？② embedding 模型 2026 年的选型格局是什么？③ rerank 模型配谁？④ "RAG vs 长上下文 vs 微调"这张决策表怎么用？

## 一、向量库选型

| | pgvector | chromadb | milvus | qdrant | elasticsearch |
|---|---|---|---|---|---|
| **定位** | Postgres 扩展，事务型应用内嵌 | 轻量嵌入式/原型首选 | 分布式大规模专用库 | 高性能 Rust 系专用库 | 全文检索老牌 + 向量补充 |
| **优点** | 与业务数据同库、SQL join、事务、备份复用 | 几行代码起服务，上手最快 | 十亿级向量、生态成熟 | 内存效率高、过滤快 | BM25 原生最强，混合检索一体 |
| **缺点** | 十亿级向量吃力 | 不适合大规模生产 | 运维组件多（etcd 等） | 社区比 ES/Milvus 小 | 向量能力是"附加项"，资源占用大 |
| **规模甜区** | 百万~千万级 | 原型/单机 | 亿级+ | 千万~亿级 | 千万级 + 强关键词需求 |
| **运维成本** | 极低（已有 PG 则为零） | 低 | 高 | 中 | 中高（多数公司已有） |
| **Java 团队友好度** | ★★★★★（JDBC 直连） | ★★★ | ★★★ | ★★★★（REST/gRPC） | ★★★★★（ES 客户端成熟） |

**给 CTRM（Java 11 + MySQL）的选型路径**：
- **P0 起步**：PostgreSQL + pgvector——与业务同库、权限过滤用熟悉的 SQL where，运维零新增；数据量百万级向量内完全够用。
- 若坚持纯 MySQL 栈：MySQL 9 已引入 VECTOR 类型，但生态与工具链尚浅，截至 2026-09 未见大规模生产案例的权威披露，建议观望或直接用 PG。
- **升舱触发条件**：向量过亿、QPS 高、需要复杂多租户隔离 → Milvus/Qdrant；关键词检索一直是主场景 → ES 一体化混合检索。

## 二、embedding 模型选型（2026-09 已核实）

| 模型 | 维度 | 最大长度 | 中文 | 部署 | 参考价 | 适用 |
|---|---|---|---|---|---|---|
| **BAAI/bge-m3** | 1024 | 8192 | 强 | 开源可私有化（单卡 8GB 级） | 免费（付 GPU） | **中文企业库默认首选**；稠密+稀疏+多向量三合一 |
| OpenAI text-embedding-3-large | 256~3072 | 8191 | 一般 | API | $0.13/1M tok | 规模化安全默认，生态最深 |
| OpenAI text-embedding-3-small | 512~1536 | 8191 | 一般 | API | $0.02/1M tok | 性价比 API 之选 |
| Voyage-3 系列 | 1024~2048 | 16K~32K | 一般 | API | ~$0.06/1M tok | 检索基准领先，长文档 |
| Cohere embed-v3/v4 | 1024 | 512~10240 | 一般 | API/可私有 | $0.10/1M tok | 与 Cohere Rerank 端到端 |
| Qwen3-Embedding（阿里） | 可变 | 16384 | 强 | 开源 | 免费 | 中文/多语言、长文本、代码 |

> 来源：pecollective.com《What Is the Best Embedding Model? A Direct Answer for 2026》、appscale.blog 2026 模型对比、openllm.wavise.com 选型指南、CSDN《主流嵌入模型总览（2026）》，均检索于 2026-09；价格为各来源引用的公开牌价，以厂商官网为准。

**选型决策树（CTRM 语境）**：
1. 数据能否出境？不能 → 开源私有化：**bge-m3**（或 Qwen3-Embedding）；
2. 能出境且要省事 → text-embedding-3-small 起步，质量不够换 3-large；
3. 检索质量是瓶颈且预算可加 → 试 voyage-3 系列，与 baseline 跑评估集对比（注意：MTEB 高 ≠ 你的语料上高，**必须用自己的评估集验证**）。

**rerank 配对**：bge-m3 → bge-reranker-v2-m3（开源配对，两阶段管线边际成本近零）；OpenAI/Cohere API → Cohere Rerank 或本地 bge-reranker（来源：appscale.blog，检索于 2026-09）。

## 三、"RAG vs 长上下文 vs 微调"决策表

| 维度 | RAG | 长上下文直塞 | 微调 |
|---|---|---|---|
| 改的是什么 | 外部知识（数据） | 单次输入（prompt） | 模型权重 |
| 知识更新 | 即时（索引操作） | 随 prompt 重发 | 重新训练（周级） |
| 成本曲线 | 建索引一次+查询便宜 | 每次查询线性付费 | 训练贵、推理不变 |
| 权限隔离 | 强（检索前过滤） | 弱 | 无 |
| 可引用审计 | 强（引用接地） | 弱 | 无 |
| 治幻觉 | 减少但不消灭 | 减少但不消灭 | 改风格/格式最有效 |
| 适合 | 企业知识问答、多租户 | 单篇深读、个人低频 | 输出风格/格式/领域语言 |
| **不适合** | 学风格、实时数值 | 高频+大库+权限 | 教新知识（易过时且贵） |

【一句话人话】微调是"培训员工"（改脑子，贵、慢、教新知识会过时）；RAG 是"给他配资料柜"（改资料，快、便宜、可授权可审计）；长上下文是"把资料全摊桌上"（随用随摊，桌子有限还费钱）。**三者常组合，不是三选一**：微调定风格 + RAG 供知识 + 长上下文处理单篇深读。

## 【本节自测】

1. **pgvector 为什么是 Java+MySQL 团队的起步首选？**
   要点：与业务同库（SQL join、事务、备份复用）、运维零新增、权限过滤用 SQL；百万级够用。
2. **什么时候必须离开 pgvector 升舱？**
   要点：亿级向量/高 QPS/复杂隔离需求 → Milvus/Qdrant。
3. **中文私有化场景的 embedding 默认选择及理由？**
   要点：bge-m3——中文强、8192 长度、稠密+稀疏+多向量、开源免费可单卡部署（来源见上表）。
4. **MTEB 分数高的模型可以直接上线吗？**
   要点：不行，MTEB ≠ 你的语料；必须用自建评估集对比验证。
5. **bge-m3 该配哪个 rerank？为什么？**
   要点：bge-reranker-v2-m3，同源配对、cross-encoder、自托管零边际 API 成本。
6. **"教模型用我们的合同语气起草条款"该用哪个方案？**
   要点：微调（风格/格式是权重的事），RAG 治不了语气。
7. **"上月点价笔数统计"该走哪条路？**
   要点：都不是——路由到业务 SQL/报表（04 进阶篇路由表）。
