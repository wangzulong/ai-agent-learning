# 04-进阶篇：高级检索与 Agentic RAG

> 【本节问题】① 父子块和 sentence-window 用什么思路提升检索质量？② GraphRAG 解决什么"向量 RAG 治不了"的问题，2026 年进展如何？③ Agentic RAG 和 Naive RAG 的本质区别是什么、和 003 的工具循环怎么对接？④ 长上下文 vs RAG 的最终裁定怎么给？

## 一、Advanced RAG：不动模型，动检索结构

### 1.1 父子块检索（Parent-Child / Small-to-Big）

- **思路**：**用小块检索，用大块生成**。子块（如 200 字）向量化，命中后返回其父块（如 1200 字）给 LLM。
- 【生活类比】用书签找章节：书签很小好翻（子块好检索），翻到后你读的是整章（父块好理解）。
- **收益**：小块的 embedding 更聚焦、相似度更准；大块给 LLM 足够上下文。一举解决"块小搜得准但答不全、块大答得全但搜不准"的两难。
- **CTRM 映射**：《点价操作手册》按节存父块、按段存子块——问"点价流程"命中"3.2 触发点价"小段，返回整节让 LLM 看到完整流程图描述。

### 1.2 Sentence-Window 检索

- **思路**：按句子向量化；命中某句后，把它的**前后 N 句窗口**一起返回。本质是"自适应父块"：上下文范围由命中位置动态决定。
- 与父子块的取舍：父子块结构固定、实现简单；sentence-window 粒度更细、上下文更贴身，但窗口大小要调。

### 1.3 多路召回（Multi-Route Recall）

- **思路**：同一问题并行走多条检索通道再融合：
  - 多查询改写：一个问题 → 3~5 个表述，各自向量检索取并集；
  - 多粒度：段落块 + 摘要块 + 表格块分通道；
  - 多库：向量库 + BM25 + （业务数据库 SQL 查询，见 1.4 路由）。
- **失败模式**：路数越多融合越难——统一用 RRF；召回噪声随路数上升，重排变成必选项。

### 1.4 检索路由（Routing）—— 常被忽视的第一道闸

不是所有问题都该走向量库：

| 问题类型 | 路由到 | CTRM 例 |
|---|---|---|
| 事实型/规则型 | 知识库 RAG | "升贴水怎么算" |
| 实时数值 | 业务 API/SQL | "CU2509 现在的点价是多少"（查行情接口，不查文档！） |
| 操作型 | 操作手册 RAG | "怎么新增点价单" |
| 统计型 | SQL/报表 | "上月点价笔数" |

**失败模式**：把"今天铜价多少"路由到知识库，检索出三天前的行情说明——灾难性回答。路由 = 一个小分类 prompt 或分类模型。

## 二、GraphRAG：为"关系型问题"补一条路

### 2.1 它治什么病

向量 RAG 回答的是"某文档里说了什么"（点对点）。但有一类问题是**跨文档关系推理**：

- "哪些客户和同一家供应商同时签了背靠背合同？"
- "A 品种的价格调整条款和 B 品种的有什么关联影响？"

这类问题的答案**不在任何单个块里**，块与块之间需要"连线"——向量检索天然不会连线。

### 2.2 原理三步

1. **实体抽取**：LLM 从全部文档抽实体（客户/品种/合约/部门）与关系；
2. **社区检测**：图算法（Leiden 等）把紧密关联的实体聚成社区；
3. **社区摘要**：LLM 为每层社区生成摘要；查询时先查社区摘要（全局性问题）或实体邻域（局部性问题），再进生成。

### 2.3 2026-09 现状（已核实）

| 事实 | 来源 |
|---|---|
| 原始 GraphRAG（微软 2024）索引成本极高（大数据集约 $33K 量级），制约普及 | Microsoft Research Blog；nemorize.com 2026 RAG 路线图（检索于 2026-09） |
| **LazyGraphRAG**（2025-06 发布）把 LLM 摘要推迟到查询时：索引成本降至全量版约 0.1%，全局查询质量持平、查询成本低约 700 倍 | Microsoft Research Blog |
| 微软 GraphRAG 库 2026-03 发布性能优化版本；相关基准工作（GraphRAG Benchmark、LinearRAG）被 ICLR 2026 接收；MIT 开源 | microsoft.github.io/graphrag |
| **混合路由成为行业共识**：简单事实→向量 RAG；多跳关系→GraphRAG；LazyGraphRAG 让全局查询路径可负担 | bestaiweb.ai / nemorize.com（检索于 2026-09） |
| 轻量路线 LightRAG（HKUDS）走"轻索引+双层检索"，2026-04 发布 v1.4.15（EMNLP 2025 论文） | LightRAG GitHub |

- **采用建议**：默认不上 GraphRAG。先问自己"问题里有没有跨文档多跳关系"；有，且 LazyGraphRAG 级成本可接受，再上。CTRM 知识库第一版用不上——合同实体图谱是第二阶段的事。

## 三、Agentic RAG：检索从"管线"降级为"工具"

### 3.1 本质区别

| | Naive/Advanced RAG | Agentic RAG |
|---|---|---|
| 控制流 | 固定管线，代码写死 | agent 的 ReAct 循环决定 |
| 检索时机 | 每问必查 | **模型决定何时查**（常识题不查） |
| 检索次数 | 一次 | **可多轮**（查→读→发现缺→再查） |
| 工具面 | 只有向量库 | 向量库 + SQL + API + Web 多工具选择 |

### 3.2 与 003 的衔接

Agentic RAG 没有任何新协议——它就是 003 专题的**工具循环（ReAct）**套用到"检索"这个工具上：

```
Thought: 用户问"上月铜点价均价与升贴水关系"——需先查规则定义升贴水，再查 SQL 拿上月数据
Action: search_knowledge_base("升贴水的定义与计算")
Observation: 升贴水 = 现货价 − 合约价 …（引用块）
Thought: 规则清楚了，还缺上月点价数据
Action: query_ctrm_db("SELECT avg(price) FROM dianjia WHERE month='2026-08' AND variety='CU'")
Observation: 均价 75230 元/吨
Thought: 两类信息齐了 → 生成带引用的最终答案
```

关键工程点：**每个工具要有清晰的 description**（003 工具规范），否则 agent 会把"查行情"路由到知识库；多轮检索要有轮数上限与成本预算。

### 3.3 什么时候值得 Agentic 化

- P0 信号：问题需要**组合多源**（文档+数据库+API）；
- P1 信号：单次检索命中率低，需要"查了再查"；
- 反指标：问题单一固定、延迟敏感——固定管线更快更便宜，别为 Agentic 而 Agentic。

## 四、长上下文 vs RAG：最终裁定

三张决定性牌（成本/新鲜度/权限）+ 一个实用结论（01 问题篇详证）：

| 决策因素 | 倾向 RAG | 倾向长上下文 |
|---|---|---|
| 知识量 | 大（10 万字级+） | 小（几篇文档） |
| 查询频次 | 高频 | 低频 |
| 知识更新 | 频繁 | 几乎不变 |
| 权限隔离 | 需要（唯一解） | 无要求 |
| 引用审计 | 需要 | 无要求 |
| 任务形态 | 查找型问答 | 单篇深度通读 |

**裁定：三者只要占一条就回不到"纯长上下文"；权限是硬门槛。** 2026 年的正确姿势是混合：小而稳的常用资料直接常驻 system prompt（省检索），大而活的知识库走 RAG，实时数值走 API——由路由层统一调度。

## 【本节自测】

1. **父子块检索解决什么两难？**
   要点：块小搜得准但答不全、块大反之；小块检索、大块生成，两全。
2. **sentence-window 与父子块的区别？**
   要点：按句索引、命中后动态取前后 N 句窗口；粒度更细但窗口参数需调。
3. **为什么"今天铜价多少"不能路由到知识库？**
   要点：实时数值在业务系统不在文档；路由到 RAG 只能答出过期数据。
4. **GraphRAG 适合什么问题？举例一个 CTRM 关系型问题。**
   要点：跨文档多跳关系推理；如"哪些客户与同一供应商同时存在背靠背合同"。
5. **LazyGraphRAG 的核心改动与效果？**
   要点：LLM 摘要从索引期推迟到查询期；索引成本降至全量版约 0.1%，全局查询质量持平（来源：Microsoft Research Blog）。
6. **Agentic RAG 与 003 专题的关系？**
   要点：无新协议，就是 ReAct 工具循环 + 把检索作为一个工具；重点是工具 description 写清与多轮成本控制。
7. **"RAG 不会死"的三张牌是什么？**
   要点：成本（线性重复计费）、新鲜度（数据操作 vs 发布动作）、权限（检索前过滤是唯一解）。
