# 01-问题篇：为什么长上下文杀不死 RAG

> 【本节问题】① 长上下文到底进步到什么程度？② "把知识库全塞进去"为什么不划算？③ "Lost in the Middle" 说明了什么？④ 权限、新鲜度这两张牌为什么是 RAG 的护城河？

## 1. 对手的实力：长上下文确实很能打

| 时点 | 上下文规模 | 意义 |
|---|---|---|
| 2023 | GPT-4 8K → 32K | 只够塞十几页文档 |
| 2024 | GPT-4o 128K、Gemini 1.5 Pro 1M | 一本 500 页手册能塞进去了 |
| 2025~2026 | 主流旗舰 200K~1M 起步 | "整个知识库塞进去"在小规模上确实可行 |

所以这不是伪问题：**在"文档少、无权限要求、不差钱"的场景，长上下文就是更简单的方案**。RAG 阵营必须回答下面四张牌。

## 2. 第一张牌：成本——线性计费 vs 常数检索

长上下文每次提问都要**重复支付全部知识**的 token 费用；RAG 每次只检索出相关的几段。

| 对比项 | 长上下文直塞 | RAG |
|---|---|---|
| 20 万字知识库，每次问 1 个问题 | ≈ 每次输入 20 万字（约 13 万 token 级） | ≈ 每次输入检索片段 2 千字（约 1.5K token 级） |
| 每问 1000 次的输入成本比 | 100 倍量级 | 1 |
| 延迟 | 首 token 延迟随上下文显著增长 | 检索几十毫秒 + 短上下文生成 |

（token 数按中文 1 字 ≈ 0.6~0.7 token 粗估，仅示意量级。）

优先级要点：
- **P0**：查询频次越高，长上下文的重复成本越致命——企业知识库恰恰是高频场景；
- **P1**：成本不仅在线上，也在开发者调试时（每次试验都全量重付）。

## 3. 第二张牌：注意力——塞进去 ≠ 记得住

Liu et al. 2023《Lost in the Middle: How Language Models Use Long Contexts》用受控实验证明：关键信息放在上下文**开头或结尾**时表现最好，放在**中间**时性能显著下降（多文档 QA 准确率可跌 20 个百分点以上）。

- 【一句话人话】长上下文不是硬盘，是"注意力带宽有限的阅读理解"——把答案埋在 50 页材料中间，模型真的会漏看。
- 【生活类比】让你开卷考一本 500 页的书，翻到答案页不难；但让你"把整本书默读一遍再闭卷答题"，中间章节必然记不清。

## 4. 第三张牌：新鲜度——上下文是快照，知识库是活水

- 长上下文：知识变更 = 修改系统提示词/重新分发文档 = 发布动作，且**每一份在用的 prompt 都要同步**；
- RAG：知识更新 = 更新索引数据 = **数据操作**，即时生效、可增量、可回滚。

CTRM 例：2026-09 公司把铜点价的最低点价量从 500 吨改成 300 吨。RAG 方案只需重嵌该规则文档的对应分块；长上下文方案要找到所有塞了旧规则的应用配置逐一修改。

## 5. 第四张牌：权限——长上下文无法做行级隔离（企业刚需）

这是**最致命**的一张牌：

- RAG：检索前过滤（`where dept = '期货部' AND tenant = 'A公司'`），无权限的 chunk **根本不进入**上下文；
- 长上下文：谁拿到 prompt，谁就看到全部。要么为每个权限组维护一份 prompt（爆炸），要么接受越权泄露。

CTRM 是多租户系统：A 租户的采购合同条款绝不能出现在 B 租户的问答里。结论：**只要知识带权限，长上下文方案在企业场景直接出局**。详见 06 生产篇"检索前 vs 检索后过滤"。

## 6. 裁定

| 维度 | 胜者 | 说明 |
|---|---|---|
| 单篇/小知识、个人使用 | 长上下文 | 简单直接，无需基建 |
| 知识量 10 万字级以上 | RAG | 成本曲线决定 |
| 高频查询 | RAG | 重复计费决定 |
| 知识频繁更新 | RAG | 数据操作 vs 发布动作 |
| 多租户/权限隔离 | RAG（唯一解） | 检索前过滤 |
| 单文档深度逐行分析 | 长上下文 | 检索会切碎论证链 |

**结论：长上下文是 RAG 的补充，不是替代。** 04 进阶篇会给出完整的三方案（RAG vs 长上下文 vs 微调）决策表。

## 【本节自测】

1. **长上下文方案的成本问题本质是什么？**
   要点：每次查询重复支付全部知识的输入 token，成本与查询次数相乘；RAG 是常数级检索。
2. **Lost in the Middle 的结论是什么？**
   要点：关键信息在上下文中部时模型利用率显著下降（Liu et al., 2023）；塞得长 ≠ 记得住。
3. **为什么说权限是长上下文的"致命牌"？**
   要点：长上下文无法做行级过滤，任何塞进 prompt 的内容对读者全可见；多租户场景直接不可用。
4. **知识规则更新时，两种方案各需要做什么？**
   要点：长上下文=发布级修改并同步所有 prompt；RAG=数据级增量更新索引，即时生效。
5. **举一个长上下文反而更合适的场景。**
   要点：单篇长文档的逐行审阅/整体摘要，无权限要求、低频查询。
6. **给领导的一句话回应"有百万上下文还要 RAG 吗"？**
   要点：成本×频次、注意力稀释、知识新鲜度、权限隔离——四个维度只有 RAG 同时满足，长上下文只在小而私的低频场景胜出。
