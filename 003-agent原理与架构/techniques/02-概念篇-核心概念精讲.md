## 卡 1：Agent 与最小公式

- **一句话人话**：Agent 是"给了一个目标后，能自己决定下一步做什么、做完自己知道停"的 LLM 系统。最小公式：**Agent = LLM + 工具 + 循环 + 目标**。
- **类比**：请了个**外派顾问**——脑子（LLM）+ 电脑和内部系统权限（工具）+ 每天来上班直到任务完成（循环）+ 一份清楚的委托书（目标）。少一样都不成：没工具是纸上谈兵，没循环是一次性问答，没目标是无头苍蝇。
- **技术要点**：学术口径 = "感知-决策-行动"循环的软件化（AIMA 的 rational agent）；工程口径（Anthropic《Building effective agents》，2024-12）= **LLM 自主决定控制流**的系统。四部件中"目标"常以 system prompt + 任务描述 + 终止条件的形式实现。
- **坑**：把聊天机器人叫 Agent——对话只是"回答"，没有"对世界采取行动并验证结果"的闭环；也别把 AutoGPT 式 demo 当 Agent 的标准形态（那是失败率最高的形态，见 06 篇）。

## 卡 2：Workflow vs Agent（定义之争的正解）

- **一句话人话**：**workflow 是代码写死路径、模型只当零件；agent 是模型自己决定走哪条路**。
- **类比**：workflow = **地铁**（线路固定，你只能选站）；agent = **网约车**（司机听你的目标，路线他自己看着路况定）。地铁便宜、准时、可审计；网约车灵活、贵、路线偶尔迷惑。
- **技术要点**：Anthropic 的切分是**控制流归属**问题：五种 workflow 模式（chaining/routing/parallelization/orchestrator-workers/evaluator-optimizer，见 04 篇）的控制流都预定义在代码里；agent 的控制流由模型在运行中生成。OpenAI 指南（2025-04）口径一致：agent = 能多步推理 + 调工具 + 自主决定下一步的系统。两者是**频谱不是二值**（见卡 10）。
- **坑**：把 orchestrator-workers 说成"多 agent 系统"——若编排逻辑（谁先谁后、怎么汇总）写在代码里，按 Anthropic 口径它是 workflow； vendors 营销文案常混用，面试要能指出区别。

## 卡 3：Augmented LLM（增强型 LLM）

- **一句话人话**：给裸 LLM 加上三件套——**检索、工具、记忆**——得到的基本作战单元，是所有 workflow 和 agent 的积木。
- **类比**：裸 LLM 是**只带一张嘴的顾问**；Augmented LLM = 配了资料库（检索）、办公系统账号（工具）、笔记本（记忆）。
- **技术要点**：Anthropic《Building effective agents》以 Augmented LLM 为唯一"building block"，五模式与 agent 循环都由它组合而成；检索/工具/记忆各自要"接口清晰、文档完备"，MCP（Model Context Protocol，Anthropic 2024-11 发布）就是统一这类连接的开放协议，2026 年已成为事实标准。
- **坑**：以为"增强"越多越好——工具集臃肿会让模型选择困难、token 成本上升；Anthropic 明确建议"少而精的工具胜过长菜单"。

## 卡 4：工具调用 / Function Calling

- **一句话人话**：模型不"执行"工具，它只输出"我想调哪个工具、带什么参数"的 JSON，**执行永远发生在你的代码里**。
- **类比**：模型是**坐在指挥室的参谋**，只能递"申请单"（工具名+参数）；真正去仓库搬货的是你的代码（执行器）。参谋递单 → 搬货 → 把结果汇报回指挥室，一轮才算完。
- **技术要点**：API 侧流程 = ①请求带 tools 定义（JSON Schema：名称/描述/参数）→ ②模型返回 tool_call（如 `{"name":"query_futures","arguments":{"symbol":"M2505"}}`）→ ③你的代码校验并执行 → ④结果以 tool result 消息追加回对话 → ⑤模型看到结果继续推理。参数不符合 schema 会被 API 层拒绝或需自行校验。
- **坑**：①工具**描述**是给模型看的——写得烂（含糊、重叠）选错工具率飙升，工具文档本质是 prompt engineering；②幻觉工具调用（编造不存在的工具/参数）必须靠 schema 校验+白名单兜底；③工具结果是模型了解世界的唯一通道，返回里塞脏数据比不给数据更糟。

## 卡 5：Agent 循环（感知-决策-行动）

- **一句话人话**：Agent 的心跳——**拿上下文 → 决定行动 → 执行 → 观察结果 → 更新上下文 → 再来，直到达标**。
- **类比**：老司机赶路：看导航和路况（感知）→ 决定变道（决策）→ 打方向（行动）→ 看新路况（观察）→ 循环；到目的地（终止条件）才停。
- **技术要点**：五步分解见 03 篇解剖；ReAct（arXiv:2210.03629）证明"推理与行动交替"优于纯思考；循环里每次模型调用都是一次 002 篇那趟前向旅程，**成本与延迟线性于循环轮数**。
- **坑**：没有终止条件的循环 = 失控成本；循环轮数是生产环境第一监控指标（06 篇）。

## 卡 6：State / Session（会话状态与事件日志）

- **一句话人话**：State 是 Agent 工作台的"桌面"（此刻它知道什么），Session 是把整个工作过程记录下来的"案卷"（发生过什么）。
- **类比**：医生会诊：**病历本**（session，append-only 事件流：几点做了什么检查、结果如何）+ **当前医嘱**（state，现在病人的状态和下一步计划）。病历本只增不改；医嘱随时更新。
- **技术要点**：state 通常 = 消息历史 + 工具结果 + 业务变量（点价场景：已抽取的要素、查到的价格）；session 是 append-only 事件日志，**独立于上下文窗口**——窗口里放不下时，session 仍在，可据此重建/压缩上下文。Anthropic 2026 Managed Agents 明确三分法：Brain（模型+harness 循环）/ Hands（工具沙箱）/ **Session（追加式事件日志）**。
- **坑**：把 state 直接等于"聊天记录"——业务系统还需要结构化状态（如"要素抽取：待确认"的状态机字段）；只存聊天记录，重启后业务进度全丢。

## 卡 7：System Prompt 与"正确海拔"

- **一句话人话**：system prompt 是 Agent 的"岗位职责书"——写太细变成脆弱的 if-else，写太空等于没写，要落在"可操作启发式"的海拔上。
- **类比**：给新员工的手册："遇到 X 情况优先查 Y"是好手册；"客户说什么就答什么"是废手册；"如果客户说 A 那么答 1，说 B 那么答 2……"是撑不过一周的手册。
- **技术要点**：Anthropic《Effective context engineering for AI agents》（2025-09）推荐顺序：**系统指令在前（最稳定）→ 记忆/知识 → 工具定义 → 对话历史（最动态）**；海拔三档示例与 001 篇"六件套"配合使用。
- **坑**：把业务规则库全塞进 system prompt——上下文腐烂加速（卡 12/06 篇）；规则该外置到工具（"查规则"工具）或检索。

## 卡 8：终止条件（Stop Condition）

- **一句话人话**：Agent 什么时候停——**模型自己认为完成、或系统强制刹车**，两套机制必须都有。
- **类比**：网约车"到目的地停"（目标达成）+ 后台"连续驾驶 4 小时强制休息"（系统护栏）。只有前者的车，司机会绕圈找路烧油；只有后者的车，半路被拖走。
- **技术要点**：常见终止条件五类：①模型不再发起工具调用（自然收工）②显式 final_output 工具被调用 ③步数/轮数预算（如 max_steps=25）④错误阈值（连续 N 次工具失败）⑤预算超限（token/费用）。OpenAI Agents SDK 的默认停止 = 模型响应不含工具调用。
- **坑**：只设 max_steps 不设"卡死检测"——模型可以在预算内浪费 25 轮原地打转；步数预算要配"行为异常早停"（同一工具同参数连续调用即熔断，联动 001 篇 agentic eagerness 的反面）。

## 卡 9：Harness（模型的外围工程系统）

- **一句话人话**：Harness 是包裹在模型外面的一切工程：循环、工具执行、状态管理、上下文组装、护栏、错误恢复、可观测性。公式：**Agent = Model + Harness**（LangChain Vivek Trivedy，2026-03《Anatomy of an Agent Harness》）。
- **类比**：F1 赛车手（模型）再强，没有车架、进站策略、遥测系统（harness）就跑不了比赛。**"如果你不是模型本身，那你就是 harness。"**
- **技术要点**：词源借自 test harness（测试脚手架）；2026-02 Mitchell Hashimoto 博文使其流行，OpenAI 随后用"harness engineering"描述其 3 人 5 个月全 agent 生成的百万行代码库实践；实证：LangChain 在 Terminal-Bench 2.0 上用同一模型（Claude Opus 4.6）仅优化 harness，名次从 30 名外进入前 5。**框架（LangGraph 等）是搭 harness 的工具箱，harness 是你最终跑在生产上的那套系统**。
- **坑**：以为换个更强的模型就能解决 Agent 的质量问题——2026 共识恰好相反：模型趋同时，**差距来自 harness 设计**（上下文策略、工具工效、错误恢复）。

## 卡 10：自主性频谱（Autonomy Spectrum）

- **一句话人话**：从"单次调用"到"全自主 agent"是一条连续光谱，越往右越灵活、越贵、越难评估——**架构设计就是在光谱上选点**。
- **类比**：出行方式谱系：喊一声附近答案（单次调用）→ 按固定路线摆渡车（链）→ 分诊台转科室（路由）→ 多科室同时化验（并行）→ 主任医师调度会诊（编排者）→ 全权委托私人医生（全自主）。
- **技术要点**：六档频谱图见本篇头图；每档的适用场景与代价见 04 篇。判据：**任务路径可预测性**——越可预测越往左，越开放越往右。
- **坑**：把频谱当"先进程度排名"——左端不是低级，是**更便宜、更可控**；生产系统的正确形态常常是"左端为主、右端局部"（点价案例：主链 workflow + 局部 agent）。

## 卡 11：Human-in-the-Loop（人在环）

- **一句话人话**：在 Agent 流程里显式埋"检查点"，高危/低置信动作停下来等人拍板，而不是事后兜底。
- **类比**：银行柜员的"复核章"——系统算得再对，转账超限额必须柜员按密码；复核不是不信任系统，是流程合规的一部分。
- **技术要点**：OpenAI 指南要求**给每个工具做风险评级**（读/写、可逆性、权限、财务影响），高危动作触发暂停+审批（escalation to human）；实现上常用"pending 状态 + 回调确认"（05 篇点价建议单就是这么实现的）。Anthropic 同样主张 agent 可在检查点询问人类。
- **坑**：把人在环当"万能保险"——审批点太密等于没自动化（每次都人工），太疏等于没有；按风险评级布点，不是平均分布。

## 卡 12：上下文腐烂与注意力预算

- **一句话人话**：上下文窗口是**有限注意力预算**，塞得越多、越旧，模型对关键信息的召回越差——这个劣化叫 context rot（上下文腐烂）。
- **类比**：连续开 10 小时会的你：会议记录越堆越厚，"刚才讨论到哪了"反而答不上。**给模型看什么、何时看，比给多少更重要。**
- **技术要点**：Anthropic《Effective context engineering》（2025-09）三大对策：**压缩（compaction**——Claude Code 在约 70% 预算时触发总结，最轻量的形式是清理陈旧工具结果）、**结构化笔记（structured note-taking/agentic memory**—— NOTES.md/to-do 外置于窗口）、**子代理（sub-agent**——脏活隔离在子代理窗口，只回传 1~2K token 摘要）。配合 just-in-time 加载（存轻量 ID，用时再取）。
- **坑**："窗口 1M 了，不用管上下文"——n² 注意力稀释是架构级的，窗口越大腐烂越隐蔽；06 篇把它列为四大失败模式之一。跨会话的完整记忆体系在 008 专题展开，这里只管"单次任务内的窗口卫生"。

<summary>答案要点</summary>

1. LLM/工具/循环/目标；目标=system prompt 职责+任务描述+终止条件。
2. 控制流预定义在代码里=workflow，模型运行时自主决定=agent；orchestrator 的拆解调度若由代码驱动则仍属 workflow。

7. 主链在"链/路由"档（A/C 环节局部 agent），判据=任务路径可预测性。
8. compaction（长对话往返）、结构化笔记（有里程碑的迭代任务）、子代理（复杂研究/并行探索）；另配 just-in-time 加载。
