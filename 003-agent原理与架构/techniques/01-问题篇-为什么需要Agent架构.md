# 01 - 问题篇：为什么需要 Agent 架构

> 【本节问题】① 单次 LLM 调用的能力边界到底在哪？② 什么样的业务信号说明该上 Agent 架构？③ 为什么不"一步到位"全用最自主的方案？④ 点价申请业务里，哪些环节是 Agent 的用武之地？

## 1. 从一个真实的翻车现场开始

**【场景】** 你给 CTRM 系统加了个"智能助手"：把客户邮件扔给 GPT，提示词写上"请根据邮件内容生成点价建议单"。

**【实际输出】** "根据您的邮件，建议买入 500 吨，价格约 3,200 元/吨，请确认。"——看似合理，实则全是编的：库存里有没有货？期货盘面现在什么价？基差条款对不对？模型一概不知道。它只能**用语言编一个像答案的答案**。

这个翻车暴露了单次调用的四大结构性缺陷，也是 Agent 架构存在的理由。

## 2. 单次 LLM 调用的四大局限（黄金圈之 Why）

| 局限 | 技术描述 | 点价场景的具体表现 | Agent 架构的解药 |
|---|---|---|---|
| **① 无状态** | 模型是纯函数：这次调用对上次一无所知 | 客户三封邮件谈同一笔生意，助手每次从零理解，前后口径打架 | state/session（02 卡6）：把会话历史与业务状态持久化 |
| **② 无行动力** | 只能生成文本，不能查库、下单、发消息 | 说不出真实库存和期货价，只能编 | 工具调用（02 卡4）：`query_inventory()` / `query_futures()` |
| **③ 单轮无反馈** | 一次生成就定稿，没有"看到结果再修正"的机会 | 抽取要素错了（把 M2505 认成 M2509），没人纠错 | 循环（03 篇）：观察工具返回 → 发现矛盾 → 重新抽取 |
| **④ 无过程控制** | 没有步数预算、终止条件、中途人工介入点 | 模型"一口气"输出结论，你想在"生成建议单后"卡一道人工确认都没有 | 循环编排 + 停止条件 + 人在环（02 卡8/卡11） |

**【生活类比】** 单次调用 = 问一位**蒙着眼、没有手机、失忆**的资深交易顾问：他再聪明，也只能给你一段"听起来专业"的话。Agent 架构 = 给他**睁眼（上下文）+ 手机（工具）+ 复述确认（循环）+ 交付标准（目标）**。

## 3. 什么信号说明"该上 Agent 架构了"

OpenAI《A practical guide to building agents》（2025-04）给出的判断依据，翻译成自查清单：

- [ ] **决策逻辑混乱或规则频繁变化**：点价规则、基差口径季度一改，硬编码 if-else 维护成本爆炸
- [ ] **输入是非结构化的**：邮件、聊天记录、合同 PDF——正则和模板覆盖不了的写法无穷多
- [ ] **需要多源交叉**：一个结论要同时看库存、期货、信用额度、历史成交
- [ ] **步数不可预知**：有的邮件一句话说完，有的夹着三个附件和一份补充协议

四条全中 → Agent 架构；中一两条 → 也许 workflow/单次调用就够（见 07 篇）。**反例警示**：纯文本润色、固定格式转换这类任务，单次调用更快更安全，上 Agent 是自找麻烦。

## 4. 为什么不"一步到位"上全自主？

因为自主性是有代价曲线的（04 篇展开）：每多一分自主，就多一分成本、延迟、不可预测性与评估难度。Anthropic《Building effective agents》（2024-12）的核心主张就是一句**反直觉的话**：

> 先找最简单的可行方案，只在证据表明必要时才增加复杂度。许多生产场景，单次调用 + 检索 + 好例子就够了。

**优先级要点（记这个顺序）**：
1. 能单次调用解决 → 不上链
2. 能固定 workflow 解决 → 不上 agent
3. 上 agent → 必须有步数预算、护栏、人工确认点
4. 多 agent 编排 → 只有单 agent 明确扛不住才考虑

## 5. 点价业务的"拆弹"：哪里值得用 Agent

```text
客户邮件进来
 ├─[A] 理解与抽取要素     ← 非结构化 → Agent 的主场（模型能力）
 ├─[B] 查库存/期货价      ← 结构化 API → 死代码工具，不需要"智能"
 ├─[C] 交叉校验与异常判断  ← 半结构化 → Agent（规则写不完：信用超限+价格异动+重复申请…）
 ├─[D] 生成点价建议单      ← 模板化 → 死代码（LLM 只负责填空）
 └─[E] 交易员确认          ← 必须人工（资金合规），Agent 无权跨过
```

结论预告（07 篇论证）：**B/D/E 用死代码，A/C 用模型**——这就是"自主性频谱"上的落点选择，也是本专题反复强调的观念：Agent 架构 ≠ 全自主，**是给每个环节配上恰好的自主度**。

## 6. 常见坑点（问题篇阶段就该记住）

1. **坑：把"接了 API"当"建了 Agent"**。没有循环、状态、工具反馈回路的，都只是 Augmented LLM 或 workflow。
2. **坑：为了炫技上全自主**。全自主 agent 的错误率随步数**复利式增长**（06 篇"雪球错误"），点价涉及资金，错一步就是事故。
3. **坑：提示词里写死所有规则**。规则库会爆炸且互相打架——001 篇"正确海拔"原则：写可操作的启发式，不写穷举 if-else。
