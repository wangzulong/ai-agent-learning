# 多 Agent 编排层：从一只到一群——当蜜蜂有了分工

> **AI Harness Engineering 系列 · 第八篇** · 王海涛（GitHub：derekwang85 · 腾讯云 TVP / 架构师名人堂）

凯文·凯利在《失控》里写过一个反直觉的观察：蜜蜂没有蜂后发号施令，蜂群也没有中心化的指挥所，但成千上万只蜜蜂却能不撞车、不争论、不内耗地完成筑巢、采蜜、迁徙。蜂后的名字里有"后"，但它并不发号施令。真正的调度，藏在每只蜜蜂判断"我该不该去采蜜、去哪采、要不要换活"的局部规则里。

这一篇要讲的东西，和蜂群是同一件事。只是我们要编的不是蜜蜂，是一群 AI。

![00-intro.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/49d39254905a39ace77e796c699ff650.jpg)

## 单个很强，不代表一群就能干活

前七篇我们都在堆约束：战略层给了方向，架构层留了决定，契约层写了规格，门禁层卡了入口，实现层保证了幂等。到这一步，一个 AI 已经能在我们划好的轨道上稳定跑完一部分活。

但真正一线的问题往往不是"单个 AI 能不能干好"，而是"好几个 AI 一起干，会不会互相踩脚"。

在很长一段时间里，我们默认的作业方式是串行：一个 Agent 从头干到尾，干完一个环节，把结果丢给下一个。这样最省心，因为只有一个人在场上，没有协调成本。可一旦任务变多、步骤变长，串行就暴露它的天花板——**时间是以加法累积的，而人（和 Agent）的耐心是减法的**。

于是我们把作业方式从"一个全能选手负责一整条流水线"改成了"一群专精选手，一人一段"。

## 转折：从一条流水线，到一张分工网

![01-division.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/f1e0f9052a4c28741e6460efec6295b2.jpg)

改动发生在两个动作上。

第一个动作，是把原来由单个 Agent 顺序完成的整段工作，拆成多条可以并行的独立子任务，交给多个 Agent 同时跑。数字验证给了我们直观的回报：原来一个 Agent 串行做同一组数字核对，稳定耗时四十五分钟；拆成七条并行通道之后，耗时被压缩到原来的一个零头。四十五分钟变成几分钟，这中间没有加任何新机器，只是让原本"排队等一个人干"的活，变成了"七个不同的人同时干"。

第二个动作是想清楚"谁来分配"。我们没有写一个中心化的"调度大脑"，而是套用了蜂群和现代操作系统的共同思路——**工作窃取（Work Stealing）**。每个 Agent 手上都有自己的任务队列，闲下来的 Agent 不去干等，而是去"偷"别人队列里还排着的活。谁空谁上，谁的队列太长谁就被稀释。

听起来像句废话，但它解决了一个真实的坑：如果任务分配是固定的、静态的，那么总会有"某个 Agent 排了超长的队，而另一个 Agent 空得无聊"的时刻。固定分工在一群人完全同质、任务完全均匀时没问题，可现实里任务永远不均匀。工作窃取的本质，是让"谁空谁干"取代"谁的名字在名单上谁干"。

## 真正的转折点看门狗：不在家的时候，谁来收尸

![02-watchdog.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/40320891908ae5c6d5d222b882c1e9e5.jpg)

拆成多 Agent 最有说服力的场景，不是省了那几十分钟，而是它带来的**自动恢复能力**。

有段时间我们被一个问题反复折磨：Agent 干到一半卡死了，而人不在电脑前。等晚上回来才看到任务超时，重新跑一遍，又是一个小时过去了。三十多分钟的空转是常态，跑久了烧的是成本，跑错了烧的是信任。

给多 Agent 架构配上**看门狗（Watchdog）**之后，逻辑整个反过来了：每个 Agent 的工作被监控，一旦某个 Agent 长时间没有心跳、没有产出、或者输出异常，看门狗不是等人工，而是直接判定它已失效，把它的任务重新分给别的 Agent，并把失效的 Agent 重启。整个检测到恢复的闭环，稳定压缩在五分钟以内。

这一条的时差，和前面那条四十五分钟变几分钟一样，不是炫技，而是把"失效"从一次事故，降级成一次例行切换。

## 一个 62% 的耳光：不是所有的活都该让 AI 一个人干

![03-62-percent.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/6adcadc803f003e804e29875cedcb1c3.jpg)

但多 Agent 不是银弹。我们踩过一个很疼的坑，值得单独拿出来讲。

公司当时跑了一个产品（内部项目，数字来自上线前抽查，受商业保密约束不展开细节），设计上是一条"大模型自主作业"的流水线——AI 自己理解需求、自己生成、自己上架。上线前的抽查里，欺诈率高达 62%[内部项目实测]。也就是说，上架的这批里，差不多每三个就有一个是坏数据。更让人后怕的是，因为流程是全自动的，这批坏数据已经顺着流水线"上架"了，只差最后一步就进入真实业务。

事后复盘，我们没把锅全甩给模型，而是看清了一个更核心的事实：**让一个大模型独立承担一条完整、关键、且涉及金钱的细分任务链，本身就是设计错误**。模型不是能力不够，是它不该在没有外部制衡、没有旁路确认的情况下"自己给自己判卷"。

后来的解法不是把 AI 砍掉，而是把它从"单打独斗"改回"有分工、有制衡"。关键决策不再由单个模型独断，而是引入多模型共识——常规的评审交给通用模型把关，风险更高的动作，让多个不同模型各自独立判断后投票，多数通过才执行。

这里顺便要提一个我们在第三篇埋下的概念：**Swarm-Fed ADR**。当时我们说"架构决定会从一群 Agent 的实操里长出来"，现在到了兑现时刻——多 Agent 跑起来之后，哪些分工合理、哪些环节老出问题、哪些通道总是空转，这些"蜂群反馈"会成为下一轮架构决策的输入。分工不是一次画死的图，是不断被蜂群自己喂肥的活物。

## 分工的终极形态是只看结果

![04-swarm-fed.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/16df1736bddbe21d65db34388bbb392c.jpg)

这个"工作窃取 + 看门狗 + 多模型共识"的骨架，在 derekinside 里可以找到一个**类比**（说清楚：这是我在此做的映射，不是 derekinside 的自有术语——它的真实架构是 Model Registry / Constraint Solver / Knowledge Graph）。

derekinside 把我们对多 Agent 的所有想象，折叠成了一个叫"通路"的机制：一群 Agent（它内部管它们叫 wings）各有分工，空转的 Agent 会去"偷"别的通路里排队的活；同时一个看门狗盯着整个体系的健康，一旦某个 Agent 沉默过久、产出异常，它会自动重启并转移负载。机制在理念上同构，但 derekinside 不是在"模仿"我们这套——它是用自己的架构（模型注册表 + 约束求解器 + 知识图谱）独立长出来的同一套分工逻辑。

用的时候你会体会到一件事：当一个任务把多个 Agent 串起来跑，你不会去关心"现在在跑的是哪一只"，你只会关心"任务本身是不是健康"。**分工的终极形态，是让人看不见分工，只看见结果。**

## 一群"看起来很忙"的 Agent，比一个懒的 Agent 更危险

![05-anti-pattern.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/b05344ad1b12c6905f0594d54c5f3b94.jpg)

我得泼一盆冷水。多 Agent 之所以诱人，是因为它看起来很高级——于是很多人会陷入"多 Agent 幻觉"：任务根本不需要拆，也硬拆成一群 Agent，让它们互相"交接"、"讨论"、"投票"，产出一大堆冗长的中间过程，最后还是那个最好的模型一句话就干完了。

编排是有成本的。Agent 越多，日志越乱，分歧越需要仲裁，协调越需要投入。**当你发现一群 Agent 在"高效地讨论"、而不是在"产出东西"时，你大概率不是在用多 Agent，你是在用一个昂贵的聊天室。**

裁量标准只有一条：**这次任务，拆开比不拆，真的更快、更强、更不容易出错吗？** 如果答案是不确定，那用串行，用单个，别为了酷而拆。

## 第一天就能用的清单

![06-checklist.jpg](https://developer.qcloudimg.com/http-save/yehe-11918656/8d3b3b559e0378527688c169cc11052b.jpg)

- [ ] **试探并行**：给每个数字验证、内容生成之类可独立的任务，先试拆成并行子任务，起点是 5-8 条通道，量好了再往上加。
- [ ] **改用工作窃取**：抽掉"任务分配表"，改成工作窃取：空闲的 Agent 去拿排队最长的活，别让空转干晾着。
- [ ] **配上看门狗**：给每个 Agent 配看门狗：沉默超过阈值就自动重启、转移负载，别等人工发现。
- [ ] **关键动作多模型投票**：凡是涉及金钱、生产环境、对外上架的关键动作，一律多模型独立投票，禁止单一模型独断。
- [ ] **回喂架构**：每过一段时间，把多 Agent 的"蜂群反馈"（哪条通道老坏、哪个分工不合理）喂回你的架构决定。

## 下一篇预告

分工再漂亮，也得先有个"脑子"——共同的记忆。一群 Agent 跑得再欢，如果每次都是从零开始、转头就忘，那它们只是在重复劳动。下一篇我们讲系列里我最想讲的一篇，记忆与知识层：derekinside 。它回答的问题是——**让 AI 记住，比让 AI 更聪明，难在哪，值在哪。**
